# Mac与PC共同维护

两端共享GitHub的代码、公开记录与规则，私有原片路径和编号登记仍在原维护端。先读根目录 [AGENTS.md](../AGENTS.md)，再看 [本轮交接](../coordination/current-batch.json)。

## 开工与分工

每端从最新`main`开自己的工作分支。开工记录：批次ID、基线提交、负责文件和是否操作私有登记。已有未提交改动先辨认并保存，不用`reset --hard`、`clean`或强推消除差异。

本轮持续集成使用Python 3.12并分别运行Windows、Linux检查；不要把Mac本地检查写成PC已经验收。

拥有本批私有`registry.json`与`mapping.json`的原维护端继续负责首次编号。Mac可修代码、生成公开阅读页、整理既有来源；PC可继续原有原片核验。另一端没有同一份私有登记时，只按已发布ID补充记录，不从目录排序重建编号。

公开交接是沟通记录，不是自动跨机锁。双方要写同一私有登记时，先在对应GitHub交接Issue中确认谁负责本批写入；其他工作可并行。实际文件锁只对使用它的同一系统和路径有效。

## PC接收本次更新

1. 保存当前任务的`progress.json`、结果与私有登记备份，保留现有核验任务目录；不停止已正常运行的核验任务来执行Git同步。
2. 在另一个干净代码副本读取最新`main`和本文件，检查本批公开目录的编号仍与原私有映射一致。
3. 在该代码副本执行下面的无原片检查。它们只检查公开文本、目录和合成测试，不执行3.5TB原片核验。

```sh
python -X utf8 scripts/archive_catalog.py validate --root .
python -X utf8 scripts/export_identity_crosswalk.py --root . --check
python -X utf8 scripts/public_reading.py check --root .
python -X utf8 -m unittest discover -s tests -v
```

4. 继续原核验任务时沿用原`--local-state`与任务目录；失败恢复参数以该版本`verify_library.py --help`及 [核验运行说明](批量核验运行.md) 为准。不重启一遍全盘扫描来补更新。
5. 核验结果先在仓库外的原私有主目录增量导入。当前Git树是有`.p4-public-scope.json`的公开投影，不能直接import；按 [公开范围投影](公开范围投影.md) 用原禁发清单、具体官方证据与明确字幕白名单生成候选公开输出。范围排除与已有编号同时保留。先看差异、运行验证，再提交本批公开记录。日志、路径、原始ffprobe响应及私有映射不提交。
6. 在GitHub用“跨端交接”Issue表单回报批次、代码提交、核验范围与下一步。未回复前，Mac端交接保持“尚未收到PC回执”，不能写成PC已完成。

## 同一套数据与生成方式

- 目录记录、官方身份对照、编辑阅读说明各有明确来源；运行生成程序统一更新INDEX、项目页和阅读入口。不要只在生成页改一个标题。
- 上游范围基线原有3份SRT与16条既有平台关联；本次PC增补保留3份正文，并加入第17条既有视频及字幕操作观察。最终数量从同版目录生成，不从旧99份字幕副本恢复；平台菜单可选、单点渲染与完整听校分开记录。
- 代码、JSON与Markdown统一UTF-8/LF；已公开SRT按原字节保留。`.gitattributes`防止Windows换行转换使字幕SHA失效。
- [身份对照](身份对照.md)可供两端和既有工具直接读取；它投影已存在的ID及对照依据，不分配新身份。
- 文件换版保存旧文件ID和历史；对当前字节相同、字幕配对、公开范围等结论重新核对其版本依据。
- 原片时间码使用`source_zero`。重剪输出另有时钟，须记录区间对应。
- 旧平台回执保留当时观察时间；现在可见、播放和字幕状态需要另记当前回读，不能只改一个`verified`字段。

## 最小交接内容

| 字段 | 内容 |
|---|---|
| batch_id | 本轮唯一批次，沿用当前批次或明确新建 |
| base_commit / result_commit | 开始与交付的Git提交；未提交时如实写未提交 |
| owner / files | 负责端和本次编辑文件范围 |
| private_state_operation | 未操作 / 原登记端增量更新；不附实际路径 |
| completed / remaining | 已完成的范围、真实未完成项与原因 |
| checks | 检查命令、结果及适宜公开的证据链接 |
| next_owner / next_action | 下一端能直接执行的动作 |

具体机器路径只通过既有私有渠道保存；公开记录使用本仓ID、批次ID和输入/版本摘要。交接不是全库上传、覆盖生产网站或删除原片的指令。

## 发布前与冲突

提交前再次读取GitHub`main`。若其他端有新提交，合并或rebase后重跑检查；只推自己分支，再通过PR合并。不能用旧JSON整份覆盖新记录来消除冲突。涉及编号、归属、版本或字幕文本的冲突，按双方来源逐项保留并解决。

代码合并、公开目录刷新、网站部署和平台发布分别回读。这个仓库的更新不自动部署P4新主站、何发站或经典保留站。
