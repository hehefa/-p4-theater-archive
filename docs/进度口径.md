# 进度怎么记

[PROGRESS.md](../PROGRESS.md) 是面向阅读的打卡页；[progress/summary.json](../progress/summary.json) 是同一份输入生成的机器可读摘要。唯一人工维护入口是 `progress/work-items.json`，不要分别改两份生成物。

开头的“批次速览”逐行显示三阶段的数量与比例，原片工序另列；详细复选框与证据保留在后面。速览也不计算或暗示全库总比例。

## 分母与阶段

每批写清 **范围、总数、单位、阶段和证据**。已整理、GitHub已发布、平台已发布独立记录，不根据上一阶段自动推定下一阶段。某批 `487/487` 只表示那份固定清单的对应阶段完成，不表示整体档案完成。

未知总数用 `total: null`，未知阶段数量用 `count: null`。显示为“未核定”，不转成0。已查明没有完成项时才写0，并附对应证据。分母为0时不生成百分比或完成勾选。百分比仅在分子、分母均已知且分母大于0时计算到一位小数；禁止手填百分比。

家庭材料及其他范围排除不属于待发布积压，不能列成“未完成发布”批次。可在顶层范围说明或 `leads` 中记为 `excluded`；不进入批次百分比。项目候选、素材文件、字幕文件、文章条目、不同语言文本、平台视频版本各有单位，不相加成为总完成率。

## 输入契约

顶层固定字段：

- `schema_version: 1`
- `as_of`：台账更新日期，或带时区的ISO时间。不是平台重新观察时间。
- `scope_note`：本页范围说明。
- `batches`：明确批次列表。
- `leads`：后续线索列表，不计算数量完成率。

每个批次：

```json
{
  "id": "fixed-release-example",
  "title": "某个明确资料批次",
  "scope": "只包含本次冻结的已公开材料",
  "total": 2,
  "unit": "份字幕",
  "stages": {
    "prepared": {"count": 2, "evidence_urls": ["https://example.org/prepared"]},
    "github_published": {"count": 2, "evidence_urls": ["https://github.com/example/repository/commit/COMMIT"]},
    "platform_published": {
      "count": null,
      "evidence_urls": ["https://example.org/scope-record"],
      "note": "平台数量尚未核定，不把GitHub公开当作平台serving",
      "observed_at": null
    }
  },
  "status": "github_published",
  "next_action": "按新的真实回执补平台阶段",
  "links": [],
  "snapshot": {
    "kind": "caption",
    "measure": "files",
    "stage": "github_published",
    "ids": ["external-edition-id-a", "external-edition-id-b"]
  }
}
```

三阶段必须显式存在。每个阶段即使数量未知，也要有非空的公开HTTPS证据列表，用以说明核对范围或未知原因；不能填本地私有路径。`note` 与 `observed_at` 可选。历史台账可以保留原观察时间和历史声明，但不能改写为今天live已验。`status` 只是本批状态说明，不决定打勾；里程碑由该阶段的明确数量是否达到本批分母决定。

`snapshot` 可选，用于对 `published/manifest.json` 直接查验的批次。提供时：

- `kind` 为 `caption`、`document`、`research` 或 `all`。
- `measure` 为 `items`（条目）、`files`（登记文件）、`video_versions`（字幕对应的准确视频版本）。最后一种只允许caption，按明确YouTube ID及记录中的发行/来源SHA版本去重，不从标题猜身份。
- `stage` 指定与这个manifest快照对应的阶段。默认分母和该阶段count必须同时等于实数，不能手填100%。其他阶段独立。
- `completed_where` 可选，仅支持items计量下的固定 `content_status` 字段与非空字符串数组。例如 `{"content_status":["captured_text","full_text","edited_public_excerpt"]}`。分母仍为选中的全部条目，该阶段只计算状态匹配的条目；不能先滤掉缺正文记录再声称100%。
- `ids` 可冻结稳定已发表条目ID；重复、不存在或kind不符均拒绝。新增文章或字幕后，这个固定批次的分母保持不变。省略ids时按当前kind全选，适用于明确标注“当前快照”的动态批次。

例如同一批554篇真实文章，目录登记可为554/554；正文恢复应使用同554个ID和上述状态条件，若538篇有正文则为538/554（97.1%），16篇metadata_only仍在分母中。生成摘要的snapshot同时给出 `actual_total`、`actual_stage_count`；`actual_count`保留原有的全批计数含义。未使用完成条件的既有批次行为不变。

不要为了记录未发布的拟办事项先把它加入published manifest；拟办事项放leads，范围明确后建立自己的批次。manifest声明、文件版本与真实发布结果仍须分别通过补充包校验和远端回读；进度工具不联网替代这些检查。

字幕语言覆盖表可以使用与snapshot互斥的 `coverage_source`，例如 `"coverage_source":"progress/caption-top10-20261024.json"`。路径只允许progress下的安全相对JSON，不能穿越目录或symlink。覆盖表schema_version为1，items每槽以 `(youtube_id, language)` 唯一；state只能为 `github_version_recorded` 或 `source_version_unresolved`。已记录槽必须有真实manifest中的 `caption_item_id`，其kind、YouTube ID与language均相符；未解决槽不冒称已记录实体。

覆盖表的 `target_language_slots`、`github_versions_recorded`、`source_version_unresolved` 必须等于实际槽数。工具强制batch.total等于全部槽数、github_published.count等于已记录槽数；不会根据“已上传”推定平台发布。覆盖文件SHA进入生成输入指纹，文件内容变化后check会要求重新生成。当前240槽中的199个准确版本因此为199/240（82.9%），其余41槽保留明确缺口，不能手填成全完成。

线索字段为 `id`、`title`、`state`、非空`evidence_urls`、`next_action`。线索状态不会自动升级为发布数量。

## 原片工序另算

生成器直接读取 `catalog/summary.json`，用 `public_selected_video_files` 作为当前候选分母，分别展示：

| 摘要字段 | 显示标签 |
|---|---|
| `full_sha256_recorded` | 完整SHA登记 |
| `full_decode_passed_existing_reports` | 既有完整解码记录 |
| `official_media_affiliation_confirmed_assets` | 官方逐项关联 |

这些比例描述不同工序，不能相加，也不是原片已发布比例。对应字段缺失或为null时显示未知，不能猜0。`public_excluded_video_files` 单独展示为范围排除，不加回待发布分母。完整私有盘点、当前候选、具体获准公开材料与全部P4历史作品不是同一范围。

## 生成、打卡与检查

```sh
python -X utf8 scripts/archive_progress.py build --root .
python -X utf8 scripts/archive_progress.py check --root .
python -X utf8 -m unittest discover -s tests -p test_archive_progress.py -v
```

更新对应批次的实际count、证据、观察时间和下一步后重新生成。输入先完整验证，失败不覆盖生成页；check只检查漂移，不修复或推送。两份生成物使用UTF-8/LF，各文件原子替换。它们可以随Git提交发布；不启动后台任务、不扫描原片、不更新平台、不修改private registry/mapping，也不创建自动提醒。
